# 08 clicks-60m

## Summary
The click phase is **572 ms of the measured 8,243 ms internal total (6.9%)**, and the only click-specific item big enough to matter is the once-per-click canonical-person probe, whose size is *bounded, not measured* (~60–150 ns/click inferred from the clicks-vs-events per-row gap). A per-worker memo in front of `PersonMap` is the only cheap change, but it has a real break-even: it pays only above a ~5–15% exact-key hit rate, so its expected value is **−35 to +200 ms** and it must be gated on a measured hit counter, not an assumed Zipf rate. Overlapping clicks with dedup is capped by stall slack that nobody has measured per phase; at 6.9% of wall it is not worth the rebase risk before the freeze.

## Current cost
Measured (`00-profile.md`): clicks **572 ms at 60M** of **8,243 ms internal** (`native start to exit` 8,561 ms; the 7,772 ms figure in `research/perf2/README.md` §1 is stale), 208 ms at 20M, **109,605 minor + 107 major faults**. Whole-process CPU is **40.867 s user + 12.389 s sys = 53.3 s over 8.561 s = 6.2 thread-equivalents**; that is a whole-run figure and **says nothing about per-phase utilization**, which is not measured anywhere.

The sample profile is a *separate serial gperftools run*: 8,541 samples at 250 Hz ≈ 34.2 s **user** CPU covering 8,479 ms internal (≈4.0 user thread-equivalents), with 12.4 s of sys time process-wide unallocated to any phase. Inference from it: `scatter::<Ck>` = 700 samples ≈ **2.80 s user CPU** ≈ 187 ns per raw click (15M) at ~4.9 thread-equivalents — a cross-run inference, not a phase measurement. Event scatter = 836 samples ≈ 3.34 s / 60M ≈ **56 ns/row**. Because both come from the same run, their ratio is more trustworthy than either absolute number; the gap (~95–145 ns/row) contains the campaign probe and the person probe, so the probe is bounded at **60–150 ns/click**, not pinpointed.

Footprint: `Ck` is **48 B, not the ≤40 B in `PLAN.md:249`** — `align_of::<u128>() == 16` on this toolchain, so 16+16+4+2 rounds to 48 (`src/v2/types.rs:45-52`; round-1 `05` reports the same, toolchain 1.97.1, `Cargo.toml` edition 2021). ~14.7M stored clicks × 48 B ≈ **705 MB**, and `prealloc_cap(bytes,45)` reserves ~828 MB across 8 tasks × 256 buckets (`mod.rs:192`). The 109,605 faults ≈ 449 MB of first touch, *less* than the array — some `Ck` pages are already resident — so treat faults as ≤30–55 ms wall (0.16–0.27 s CPU), an upper bound, not a 705 MB bill. Verify with `size_of::<Ck>()` before any capacity reasoning.

Validity/fallback facts that any change must preserve: click window `[start−7d, end)` (`parse.rs:113`, `rules.md:36`); `Ck.ts` fits `u32` because `Ctx::build` rejects span > `u32::MAX` (`types.rs:99-102`); a campaign >15 B → `Skip`, legal only because `Ctx::build` returns `None` for any such key; `user`/`click_id` >15 B → `Overflow` → whole-run V1 (`parse.rs:116`). D7's no-click-dedup is a true no-op (`rules.md:61-62,66,122`), so *adding* click dedup is the illegal move.

## Details
**1. Memo.** `person()` is one SwissTable probe (`people.rs:15-18`) into a table of ~1.2–3 M `u128→u128` entries (tens of MB at 60M). A per-task direct-mapped memo persists across the chunks that task pulls, so scattered rows are irrelevant to *hit rate* — but that is precisely why no hit rate may be assumed: it is a property of the click distribution and of collisions in 512 slots, and must be counted. Cost model per row: `id::mix` (~6 cycles) + one 32 B L1 slot load + a 16-byte compare + branch ≈ 3–6 ns on hit, 5–9 ns amortised with the miss path. Because the map is immutable after P1, caching the *answer* `person = user` is safe and needs no separate validity state. Prefer 512 × 32 B = 16 KB (half of a 32 KB L1D) over 1024 slots (32 KB = whole L1). If an explicit valid tag is preferred, a 48 B slot forces 256 entries. Wall gain must be divided by the phase's actual parallelism, which has never been measured; do not reuse the whole-process 6.2.

**2 vs 3.** Dedup is the better host: clicks need only `people`/`ctx`, dedup only `ev_parts`, so no ordering exists. Neither removes click work, and both targets move when `dedup-arch` replaces P2.

## Rejected ideas
- **Add click dedup (D7 reversal):** 1–3% identical copies; a hash pass over ~700 MB costs more than the duplicate work it removes, and could only change output if copies differed.
- **Shrink `Ck` 48→32 B:** 16 B × 14.7M ≈ 235 MB, ~15–30 ms here; needs a person ordinal or truncated `click_id`, which breaks the `u128` merge-join (`sessions.rs:186-188`) or the smallest-`click_id` tie-break. Cross-track (`sessions-60m` #4).
- **Presize tuning:** the 1.15 factor already reserves 828 MB against 705 MB used; faults are first touch, not doubling.
- **Click-specific scanner / ts-first reordering:** ~40–90 ms best case, med risk (F1/F2/F3, `\r`, A6/A10), and `scan-avx2` builds the general version.
- **`_mm_prefetch` on the probe:** hashbrown exposes no slot address; a custom table is 2× the work for the same misses.

## Dependencies / conflicts
`memory-traffic` and `sessions-60m` (`Ck` width/faults), `dedup-arch`/S4-1/S4-2 (ideas 2–3 must rebase; the memo's `mod.rs:242` use belongs to the person/dedup card and must not be double-counted), `critical-path` (utilization), `scan-avx2` (supersedes the scanner idea).
